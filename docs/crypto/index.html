Engineering field note · protocol, measurements, open questions

Cryptography is a chain of decisions.

Pulse-Vault owns a Go API, versioned file formats, and the rules that bind them together. It does not claim to invent a cipher. This page opens up that design: what the current stream does, what the benchmarks actually measure, and where careful research could take the library next.

01 · The system, not a cipher

What the package owns

A useful crypto package is more than a call to Encrypt. It defines which bytes have meaning, which keys may touch them, how failure is detected, and how tomorrow's reader can still open yesterday's files.

Project-owned contract

Format and composition

  • Stable stream identifiers, chunk framing, compression flags, lengths, and terminal records.
  • How salts and KDF parameters are recorded, bounded, validated, and interpreted.
  • Subkey roles, nonce derivation by record index, and authenticated data that binds framing to ciphertext.
  • Container metadata, encrypted paths, file-level digests for post-decryption integrity checks, and migration rules.
  • A public Go package at gui-go/crypto that gives callers a stable interface over these rules.
Maintained primitives

Implementation blocks

  • Go's crypto/aes and crypto/cipher packages for AES-GCM.
  • golang.org/x/crypto/chacha20poly1305 and scrypt.
  • Go's crypto/rand for salts and nonces.
  • zstd for compression before encryption when the result is smaller; old XZ streams remain readable for compatibility.

Owning the API is valuable; replacing mature cryptographic implementations with home-grown ciphers is not the goal.

Own the protocol boundary. Reuse the primitive. Format design is the project's responsibility; primitive design and implementation should benefit from broader scrutiny.

02 · Current V6 stream

A stream is a sequence of authenticated records.

Large files are processed incrementally. V6 frames each data record with its length and kind, then binds the stream header, nonces, record type, and index into the record's authenticated data.

Why two AEAD passes?

The current format deliberately cascades two authenticated-encryption constructions. Each stage has its own 32-byte subkey and fresh per-stream nonce material. The outer AES-GCM stage authenticates the inner output, and each record's additional authenticated data (AAD) binds the bytes to their V6 context. This is the implemented construction, not a claim that “two ciphers means twice the security.” Cascades add code paths and assumptions, so they deserve explicit analysis and independent review.

Why an end record?

A valid sequence of earlier records cannot prove that the file was not cut off after one of them. V6 therefore writes an authenticated terminal marker and rejects a missing terminator or trailing bytes. Record index, kind, header, compression flag, and nonces are included in AAD, making reordering or header edits fail authentication instead of silently changing interpretation.

Protocol details for the curious

V6 begins with PV6STRM1, a compression flag, a 16-byte ChaCha base nonce, and a 12-byte AES base nonce. Each following record contains a one-byte kind, a four-byte big-endian ciphertext length, and the ciphertext. Data records use kind 0; the terminal record uses kind 1 and encrypts PULSEVAULT6-END.

For record index i, the first 12 bytes of each base nonce are XORed with the big-endian encoding of i. The AAD contains the magic, compression flag, both base nonces, record kind, and index. Readers enforce chunk-size limits, authenticate every record, require the final marker, and reject trailing data.

V3–V7 metadata uses the same two-pass AEAD ordering. Older formats remain supported through explicit compatibility paths; old identifiers are never silently redefined. The byte-level contract is documented in CRYPTO_PROTOCOL.md.

03 · A number with its unit attached

71.4 µs is ZIP path validation.

That figure is easy to misread. It is not a cipher timing, a password unlock time, or an end-to-end file operation.

After · segment scan 49.4 µs
1.45× faster 1,005 → 5 allocations/op

The workload: the benchmark constructs synthetic ZIP entry headers in memory and calls the vault's validateZip function. For each run, that function checks path segments, duplicates, sizes, and entry policy. The benchmark does not open an archive, read a disk, derive a password key, or encrypt data.

The change: the former implementation used strings.Split to allocate a slice for every path. The new implementation scans slash-delimited segments with strings.Cut while retaining the same path-safety checks. At 1,000 entries, the median moved from 71.4 µs to 49.4 µs and allocated bytes fell from 86,608 to 54,608 per operation.

How to read it: three one-second Go benchmark runs; report the median. That improves this validation subtask. It does not imply that all vault opens are 1.45× faster, because KDF, disk, archive parsing, and other work dominate different operations.

Reproduce from gui-go/: go test ./internal/vault -run=^$ -bench=BenchmarkValidateZip -benchmem -benchtime=1s -count=3. See the full measurement notes.

04 · Different resources, different questions

RAM does not mean speed.

Memory, throughput, latency, and allocations are separate dimensions. Sometimes lower allocation makes a path faster. Sometimes memory is intentionally spent to make password guessing costlier.

How long this operation took for this input, under this run's environment. Stream encryption includes framing and compression selection; CLI stages include filesystem and archive work too.

Resident memory sampled by the CLI harness every 20 ms. A short-lived peak between samples may be missed. RSS includes more than Go allocations, including stacks, mappings, and runtime state.

Intentional memory cost

Scrypt spends memory at unlock time.

The Scrypt memory term is approximately 128 × N × r bytes. The standard profile (N=32,768, r=8, p=1) has a 32 MiB ROMix memory term. The hardened profile (N=1,048,576, r=8, p=1) reaches 1 GiB before implementation overhead. These numbers are derived from parameters; they are not a captured process RSS reading.

That cost is for password guessing resistance. It is not an optimization target for file encryption, and it does not make bulk encryption faster. A slower unlock can be deliberate; a slow stream loop usually is not.

The isolated V6 stream measurements are separate: 0.25 ms for a 4.14 KiB repeated sample, 0.72 ms for roughly 1 MiB repeated data, and 6.15 ms for 10 MiB random data. The benchmark excludes Scrypt and ZIP rewrites. Its bytes/op values are not peak RAM. Full tables and workload definitions live in the performance explorer.

05 · Evidence, not ceremony

What has been exercised.

Cryptographic code is tested through its failure paths as much as its happy path. A passing suite is necessary evidence, but it cannot prove the design secure.

01

Known answers & compatibility

Deterministic vectors pin down key derivation, nonce inputs, AEAD composition, and historical formats. Cross-language fixtures make format drift visible.

02

Tampering & stream boundaries

Tests alter ciphertext, truncate records, reorder or corrupt framing, remove the terminal marker, and append trailing bytes. Decryption must reject data that does not authenticate.

03

Resource and parser limits

Persisted KDF parameters and archive records are bounded before expensive allocation or processing. Path validation rejects traversal and unsafe member names.

04

Fuzz and lifecycle checks

Fuzz targets exercise malformed stream input; vault tests cover create, unlock, verify, restore, delete, password rotation, and compatibility. CI runs tests and vet for the Go code.

The honest boundary

Tested is not audited.

Automated tests can find implementation defects in cases they reach. They do not replace an independent cryptographic review, a protocol proof, side-channel assessment, or operational review across supported platforms.

The project roadmap explicitly calls for external review before broader security claims or a stable-format claim. No “unbreakable,” “military-grade,” or “impossible to reverse engineer” promise belongs here.

06 · Research agenda, not a feature checklist

Where could a Go crypto library go?

“Our crypto package” can mean a project-owned interface and protocol implementation. The most responsible expansion is to make correct use easier, make evolution explicit, and let new primitives enter only with a clear threat model and a migration story.

I

Make the safe path the obvious path

Today the public package exposes byte-slice keys and format-specific functions. A future API could model a vault key, salt, KDF record, suite identifier, and stream lifecycle as distinct types, reducing accidental key/nonce swaps. It could provide one “seal file stream” path that selects a versioned suite, generates nonces internally, authenticates its own framing, and returns errors with stable categories.

That is an API-hardening project, not a new primitive. It should keep escape hatches narrow, preserve old readers, and avoid APIs that encourage callers to choose cryptographic details ad hoc. Go interfaces and small value types can express ownership without building a framework bigger than the vault.

II

Study a versioned KDF migration

Scrypt remains the current V3–V7 password KDF. Argon2id is a serious research candidate because it was designed as a memory-hard password-hashing function and has a published specification with test vectors. The question is not “which name is newer?” It is how the profile behaves on the slowest supported desktop, under concurrent unlock attempts, on low-memory systems, and against realistic password guessing hardware.

A responsible migration would define a new KDF identifier, record validated parameters, cap work and memory before allocation, benchmark cold and warm runs across supported targets, and ship known-answer plus old-format compatibility tests. Existing Scrypt files would remain readable. Parameter increases should be explicit and measured; copying a large server recommendation into a desktop app can turn a safety control into a denial of service.

Research question: can the app offer a profile calibrated to a target unlock delay while preserving a safe minimum, clear memory ceiling, and the ability to open the vault on the owner's other devices?

III

Re-examine the stream construction, not just its speed

A next format could compare the current two-stage AEAD cascade with a single-AEAD stream design using independently derived per-purpose keys. The comparison must include nonce collision bounds, record limits, misuse resistance, AAD coverage, truncation behavior, error uniformity, and failure containment—not just throughput.

XChaCha20-Poly1305 is available in Go's extended crypto module and uses a 24-byte nonce. It may simplify safe random nonce generation in a future suite, but adopting it would not make old streams safer retroactively and does not remove the need for per-record nonce discipline. A new primitive means a new version, vectors, migration rules, and external review.

Compression should stay before encryption and only be kept when it reduces size. Encrypted output should not become a compression oracle for attacker-controlled secrets mixed with attacker-visible content; current vault streams encrypt user files independently, and future archive features should preserve that separation.

IV

Make key rotation a deliberate format property

The current password-derived key protects the vault's encrypted content and metadata. A future envelope could generate a random data-encryption key (DEK) and use a password-derived key only to wrap that DEK. The benefit is narrow and concrete: changing a password could rewrap a small key record instead of decrypting and rewriting every file.

The cost is a new trust boundary and more state. The envelope must authenticate its version, vault identifier, KDF parameters, and wrapped key together. It needs crash-safe replacement, corruption handling, and old-format readers. Password loss must remain permanent unless a separately reviewed format explicitly changes that promise.

Research question: does the reduced rotation cost justify a new envelope format for this local file vault's expected size and usage?

V

Prepare for public-key recipients only when sharing exists

Go 1.27 includes a standard-library ML-KEM package. A KEM establishes a shared secret; it does not encrypt a file stream or authenticate the sender by itself. It becomes relevant if Pulse-Vault gains recipient sharing: establish a per-recipient secret, derive a wrapping key with an agreed key schedule, and use that key to wrap a random file key. If recipients must know who sealed the envelope, add an explicit sender-authentication design.

For a single-user offline vault, post-quantum KEM support may add format and key-management complexity without solving a present problem. The cryptographic library can watch the standard, preserve an algorithm-agility seam, and wait for a concrete sharing threat model rather than adding a checkbox.

VI

Make evidence reproducible by design

Every new suite should arrive with frozen vectors, property and fuzz targets, tamper matrices, adversarial resource tests, cross-version fixtures, and benchmarks that name their boundary. Performance results should report latency, allocation volume, and sampled RSS separately, on reproducible synthetic inputs.

Where possible, test one invariant at a time: a byte flip must fail authentication; one missing terminal record must fail close; a resource-exhausting KDF record must be rejected before expensive allocation; a legacy fixture must still open; cancellation must leave the prior vault intact. Measurements are most useful when their limits are as visible as their wins.

07 · A design space, not a promise

What could a larger Go library become?

The present public package is a thin, project-owned facade over the vault's internal crypto code. Expansion should begin by making its contracts easier to reason about. These are research directions: each needs a written threat model, compatibility plan, and evidence before it becomes a format or API.

01 · Names and types

Make invalid combinations harder to express.

Today the public API passes keys as []byte, and profile choices are represented by ordinary values. A later API could distinguish a password-derived key, a file data key, a nonce, and a suite identifier with separate types. It could replace mutable global profile maps with immutable lookup functions and validated value objects.

The goal is not type-system theater. Types help only when they prevent a real mistake: using a key for the wrong purpose, pairing parameters from different versions, or calling a test-only deterministic-nonce path in production code.

02 · Key hierarchy

Separate access from stored data.

A future envelope could generate a random data-encryption key for file content, then wrap it with a key derived from the vault password. Changing a password could rewrap that small data key instead of decrypting and re-encrypting every file.

This changes the file format and migration path, but not the current recovery promise: losing the password means losing access. The design must authenticate the wrapped key and KDF parameters together, preserve crash-safe replacement, and keep old vaults readable.

03 · Stream contract

Let the format own the record boundary.

A typed stream API could own header validation, per-record nonce construction, AAD, limits, final-record checks, and consistent failure handling. Callers would provide readers and writers without selecting low-level cryptographic ingredients for each file.

It must also define what a failed write means. A correct stream can still leave a partial destination behind; the vault layer needs a temporary-file and atomic-replacement contract around it.

04 · Resource honesty

Model the cost before doing the work.

Every on-disk KDF parameter should be parsed and checked against memory, work, and concurrency budgets before derivation begins. A library could expose estimates for a selected profile, while keeping policy decisions explicit for each device class.

For key and plaintext lifetime, Go makes strong erasure promises difficult: garbage collection, compiler copies, and runtime behavior complicate zeroization. The useful direction is to minimize secret copies, keep lifetimes narrow, avoid logging, and document residual limits rather than claim that a wipe is proof of removal.

05 · Versioned suites

Change the protocol by migration, never by surprise.

A suite descriptor can name a KDF, key schedule, AEAD construction, nonce rule, and stream framing. But algorithm agility can become a maze of rarely used branches. The smallest useful registry may have one writer suite and a finite set of read-only legacy suites.

Writers can move forward while readers preserve old files. A version number should select one complete, frozen interpretation; it should never silently reinterpret old bytes under new rules.

06 · Evidence interface

Make every claim reproducible.

A serious package would ship frozen byte vectors, compatibility fixtures, malformed-stream corpora, fuzz targets, resource-limit tests, and benchmark inputs with clear boundaries. Each result should say whether it includes the KDF, compression, archive I/O, or only the stream primitive.

That evidence lets downstream Go programs ask what guarantee they are receiving. A passing test shows a behavior held for tested cases; an independent review asks whether the whole construction deserves trust.

Questions that resist a one-line answer

Every capability buys something and asks for something.

Two AEAD layers or one?

The current cascade is implemented and its test vectors matter for compatibility. Whether a future format should keep it is a separate research question: a cascade is not automatically more secure, and any claimed risk reduction depends on precise assumptions. Compare a documented threat model, nonce bounds, independent keys, failure behavior, and external analysis before comparing speed.

More KDF memory or a usable unlock?

Memory-hard work raises the cost of guesses, yet a profile that exhausts a small machine can prevent its owner from opening their own data. The design problem is a bounded policy across devices and concurrent requests, with parameters checked before expensive allocation and their interpretation bound into the versioned format.

Password recovery or permanent lockout?

Pulse-Vault currently has no password recovery. Adding a second way to open a file vault would change who can reach its contents and how the format must survive compromise. Unless that threat and authority model are explicit, the honest contract is that a lost password means a lost vault.

File privacy or metadata privacy?

Encryption can hide content while leaving file count, approximate sizes, update patterns, and archive structure visible. Padding and metadata encryption may reduce leakage but cost space, speed, and usability. The threat model should say which observations matter before the format pays those costs.

Future flexibility or a small trusted core?

A plugin system sounds future-proof, but every selectable mode is code that must be reviewed, tested, documented, and supported. A narrow versioned suite list can be more durable than unlimited agility because it makes the set of possible interpretations finite.

A disciplined path from question to code

Let the evidence earn the feature.

  1. Name the adversary.Write down what they can read, modify, replay, observe, and control.
  2. State the invariant.Describe what must always hold: no unauthenticated record reaches the destination, and all-or-nothing consumers stage output until the terminal record validates.
  3. Compare constructions.Use standards, prior analyses, vectors, and measured constraints; do not invent a primitive to make the project feel original.
  4. Prototype outside the file format.Exercise failure cases and platform limits without making experimental bytes permanent user data.
  5. Review and migrate deliberately.Get independent eyes, freeze the format, preserve readers, document recovery, and only then choose a writer default.

08 · A research map for the Go package

Grow the contract before growing the algorithm list.

The package can become more useful without becoming a cryptographic framework. Its highest-value expansion is a small set of layers that make parsing, resource policy, key ownership, stream completion, and compatibility explicit. The layer names below are a design sketch, not an implemented API.

01ParseRecognize a frozen format version; reject malformed lengths.
→
02BoundCheck KDF, record, file, and concurrency budgets before work.
→
03UnlockDerive or unwrap a key under the declared vault password policy.
→
04AuthenticateVerify each record into a private staging destination.
→
05CommitRequire terminal proof and EOF before publishing output.

The format layer can authenticate records; the vault layer must make filesystem replacement transactional. A generic io.Writer cannot promise rollback after it has accepted bytes, so all-or-nothing restore needs a staging contract above the cipher.

Layer A · Frozen suite identifiers

One version, one interpretation.

A suite identifier should select a complete contract: KDF, key schedule, AEAD, nonce rule, AAD encoding, record framing, and terminal behavior. Old identifiers stay read-only and keep their exact meaning. The default writer can move forward without making old files ambiguous.

Prefer a finite registry over caller-defined cipher plugins. A plugin interface sounds flexible, but every combination multiplies the state space reviewers and compatibility tests must cover.

Layer B · Validated derivation policy

Reject hostile costs before paying them.

Parse stored KDF fields into a validated value before allocating memory or starting work. Bound memory, work, output length, and concurrent derivations independently. The KDF choice and parameters belong to the format so a future reader does not guess what the writer meant.

Keep a test-only low-cost profile impossible to select in ordinary production flows. Keep error categories useful to local callers without turning a future network endpoint into a password-validity oracle.

Layer C · Purpose-separated keys

Make key roles visible in code.

Today V3–V7 derive 64 bytes with Scrypt and split them into two 32-byte AEAD keys. That byte layout is part of the existing protocol. A future version could derive a master secret and expand labeled keys for stream encryption, metadata, and key wrapping using a specified KDF such as HKDF.

Labels are useful because they make context and role separation explicit. HKDF expands key material that is already pseudorandom; it is not a replacement for the password-hardening KDF and should not be fed a human password directly. Labels do not create extra entropy or prove a construction safe by themselves. Any changed schedule needs a new identifier, known-answer vectors, old-reader tests, and review.

Layer D · File data key and password wrap

Separate data lifetime from password lifetime.

A random data-encryption key could protect file contents while a key derived from the vault password wraps it. A password change would then rewrap that small key record. This is a file-vault rotation proposal, not a recovery mechanism: losing the password would still make the vault unavailable.

The format must bind its KDF parameters, salt, vault identity, version, and wrapped key as authenticated context. Replacement must be atomic; a crash must leave either the old valid vault or the new valid vault, not a half-written envelope.

Layer E · Stream and container boundary

Make completion a first-class result.

The stream reader owns length limits, record order, nonces, AAD, authentication, terminal markers, and trailing-byte rejection. The vault owns archive paths, destination policy, temporary files, cancellation, and atomic replacement. A caller should be able to tell whether the stream was fully authenticated and whether its destination was committed.

Do not let unauthenticated bytes reach application code. Per-record authentication does not prove that a stream was complete until the terminal record has been checked.

Layer F · Reproducible evidence

Ship the argument alongside the code.

A format release should include byte-for-byte vectors, compatibility fixtures, malformed-input cases, resource-limit tests, fuzz targets, and benchmark sources. The test suite should map each invariant to a test that fails when the invariant is violated.

Keep benchmarks separate for KDF, record sealing, compression selection, archive work, and filesystem commit. Otherwise a fast primitive can hide a slow operation, or an expensive KDF can be mistaken for slow encryption.

09 · Questions to earn with experiments

The useful research is in the boundary cases.

Algorithm names are the easy part to list. The harder work is to understand how primitives behave inside this file format, under realistic failure, across a decade of readers, and on the machine that must open the vault.

Password guessing

Scrypt today; what would justify a KDF migration?

Argon2id, specified in RFC 9106, is a serious candidate to measure. Its published profiles are not drop-in desktop defaults. Compare memory, latency, parallelism, and concurrent unlocks on the slowest supported hardware, while modeling attacker hardware and the cost of denial-of-service inputs.

Preserve old Scrypt readers. Record the new KDF identifier and bounded parameters. Decide password byte encoding and Unicode normalization explicitly; changing either can make a correct password stop matching an old vault.

Key separation

Does a labeled key schedule improve the next format?

The present V3–V7 schedule splits one 64-byte Scrypt output between two primitive keys. A future version could use HKDF with labels bound to the format and role, so stream, metadata, and envelope keys are derived for distinct purposes.

The experiment must state the property sought, account for the password KDF as the expensive step, and prove the encoding with test vectors. The mere presence of HKDF would not make the current format defective or automatically make a new one safer.

Authenticated streams

Is the current two-AEAD cascade worth retaining?

Compare it with a single-AEAD record stream using independent keys. Count nonce uses per key across files and restores, check index exhaustion, bind every interpretation-changing header field, and document what a partial write leaves behind.

AES-GCM-SIV in RFC 8452 is a candidate to study when nonce repetition is a meaningful risk. Misuse resistance reduces one failure mode; it does not remove the need for limits, framing, authentication, or careful handling of plaintext before verification.

Availability

Can a valid vault become a denial-of-service input?

Measure what happens when headers request maximum legal Scrypt costs, many files are opened concurrently, compression expands data, or a stream ends at every possible byte boundary. An attacker may not break the cipher; they may only need to exhaust memory or leave a partial restore behind.

Set independent ceilings for per-operation work, aggregate concurrency, archive entry count, decompressed bytes, and temporary disk use. Validate before allocation and make cancellation leave the last committed vault intact.

What the file reveals

Which metadata is worth hiding?

Encrypted file bodies do not necessarily hide total size, file count, approximate lengths, update timing, or whether two backups are similar. Padding and metadata encryption can reduce some leakage, but add space, work, and complexity.

Write down an observer model first: someone who can read a copied vault, compare two versions, or monitor filesystem activity sees different things. Protect only the metadata that matters to a named threat.

Persistence and rollback

Can an old but valid vault be detected?

Authentication proves that bytes were created under a key and have not been altered. It does not prove that they are the newest bytes. Replacing a current file with an older, valid copy is a rollback problem.

A purely local file cannot reliably know that an external copy is newer unless some trusted state lives elsewhere. The honest choice may be to document rollback as out of scope rather than add an online dependency or a hidden counter that can itself be reset.

10 · A research program with stopping rules

Let every proposal say what would change our mind.

Ideas become safer when they can fail a test, lose a comparison, or be set aside. This order keeps format changes behind evidence instead of letting novelty drive the protocol.

  1. First · Specify

    Name assets, adversaries, and invariants.

    Write what the adversary can copy, alter, replay, truncate, observe, and supply as input. State what must remain true: no unauthenticated record is consumed, no unbounded KDF runs, no failed replacement destroys the prior vault, and old format bytes keep their old meaning.

    Stop if: the feature has no threat it addresses or its guarantee cannot be distinguished from the current format.

  2. Second · Compare

    Prototype outside permanent vault files.

    Use disposable inputs, the same compiler and workloads, and one changed variable at a time. Measure end-to-end unlock, stream sealing, allocations, sampled process memory, and restore time separately. Include small, large, compressible, and incompressible data.

    Stop if: the claimed benefit disappears under the real workload, breaks constrained machines, or costs more compatibility surface than it buys.

  3. Third · Attack

    Turn every invariant into a failure test.

    Mutate each header field, flip ciphertext bits, truncate every record boundary, reorder chunks, append junk, corrupt KDF parameters, exhaust storage mid-write, cancel at each stage, and fuzz the parser. Cross-check fixed vectors against an independent implementation when available.

    Stop if: the parser has ambiguous states, plaintext escapes before authentication, resource limits can be bypassed, or recovery behavior is unclear.

  4. Fourth · Review

    Ask independent reviewers before format adoption.

    Publish a compact protocol specification, test vectors, implementation boundary, benchmark method, and migration plan. Request review of the construction and its use, not only a code-style pass. Keep experimental writers opt-in until the review findings are resolved.

    Stop if: review identifies unresolved design questions. A release date is not evidence.

  5. Finally · Migrate

    Make the new writer boring and old readers dependable.

    Give the format a new identifier, ship a compatibility fixture, preserve read-only legacy paths, and make upgrade atomic and recoverable. Document which properties change, which do not, and how the owner can verify the result.

    Stop if: migration requires guessing, silently rewrites without a recoverable boundary, or strands older vaults without a clear reader path.

A standards watch, not a feature promise

Post-quantum tools have a job only when the product has recipients.

NIST FIPS 203 ML-KEM defines a key-encapsulation mechanism for establishing a shared secret; it does not encrypt a file by itself. Go provides crypto/mlkem in the standard library. That becomes relevant if the vault gains a reviewed recipient-sharing design: establish a per-recipient secret, derive a wrapping key, and wrap a random content key before using symmetric AEAD for the file. KEM alone does not identify the sender. It is not a reason to complicate a single-owner offline vault today.

Before fixing any interoperable encoding to a standard, check its current errata and implementation guidance. For this repository, “keep the seam small and monitor the standard” is a complete research outcome; shipping an algorithm checkbox is not the goal.

11 · A working philosophy

The library should get smaller as understanding gets better.

A vault is a promise made by one moment to another: the writer today seals bytes; a future reader must identify their format, derive the right key, detect damage, and recover meaning without guessing what the author intended. Compatibility is therefore not nostalgia. It is care for the future person who depends on an old file.

Cryptography rewards subtraction. Every extra mode, flag, hidden fallback, and layer becomes another interpretation that a reader, tester, maintainer, or future format must get exactly right. The ambition is not maximal algorithm count. It is a small set of explicit contracts, each tied to a threat it addresses and a test that would fail if that contract broke.

There are two kinds of opacity. The attacker should lack the secret needed to open the vault; the maintainer should not lack a clear account of why the format is safe to use. Hiding the recipe does not create the first kind of protection. Documentation, public vectors, and review reduce the second kind of ignorance.

Security is not produced by obscurity. A person may inspect the source, disassemble the application, or parse the vault container. The protection claim should survive that inspection because the design depends on a secret key and sound authentication, not on keeping the recipe hidden. This is why the protocol is documented and why “impossible to reverse engineer” is not a target.

Optimization is also a form of explanation. “Faster” is not a property of a code change in the abstract; it is a measured result for an identified workload. Fewer allocations can reduce pressure without changing latency. A memory-hard KDF deliberately spends resources to raise guessing cost. A disciplined library can say both things without contradiction.

Even “the user has the key” is a human question as well as a mathematical one. Is the password remembered, backed up, or recoverable by another person? Strong cryptography can make these choices unforgiving. A thoughtful design exposes the choices and their consequences instead of disguising them as a technical default.

The project's plausible contribution is not a new cipher. It is a careful Go implementation of a local-vault protocol, with a readable public API, explicit format evolution, measured engineering, and enough humility to make review part of the roadmap.

A format is a message sent forward through time. Its author will eventually be absent: the maintainer may have changed jobs, the laptop may be gone, and the original dependencies may no longer build. The bytes must still say what they mean. That is why a protocol should prefer a few explicit states over clever fallback, and why compatibility is a security property as well as a convenience.

There is a quiet moral dimension to an encrypted file vault: strong access control can become a permanent lockout, while easier recovery can become a second door an attacker can use. The design cannot make that tension disappear. It can state the choice clearly, count the authorities that can open the files, and avoid calling irreversibility a feature when it is actually a usability failure.

The right measure of a library is not how many algorithms it can name. It is how much uncertainty it removes for the caller, how few states it asks a reviewer to hold in mind, and how clearly it admits the risks that remain. Sometimes research adds a layer. Often its best result is a reason not to.
